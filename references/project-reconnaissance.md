# Project reconnaissance and overview format

Build this codebase model before judging individual controls. Derive every statement from the
repository or supplied deployment evidence. Mark unknowns explicitly; do not replace missing
facts with framework defaults or generic assumptions.

Keep the overview concise and evidence-led. Cite the file or configuration that supports material
claims. Treat versions as known only when a manifest, lockfile, runtime file, image tag, or generated
build metadata establishes them.

## Contents

- Required artifact header
- Scope and existing documentation
- Purpose and maturity
- Technology inventory
- Architecture and delivery
- Data and trust boundaries
- Identity and access
- Entry points and integrations
- Configuration and environments
- Documentation discrepancies and open questions
- Reporting and human review notes

## Required artifact header

Start the generated file exactly with a Vibecheck ownership marker and these fields:

```markdown
<!-- Generated by vibecheck-precheck. Human review is required before the default full scan. -->
# Technical overview

- Review status: DRAFT
- Reviewed by: Not reviewed
- Reviewed at: Not reviewed
- Review scope: `<absolute or repository-relative scope>`
- Generated at: `<ISO-8601 timestamp>`
- Git commit: `<commit or Not a Git worktree>`
- Workspace fingerprint: `sha256:<digest>`
- Files fingerprinted: `<count>`
```

Use only `DRAFT`, `HUMAN-REVIEWED`, or `REVIEW-BYPASSED` for `Review status`. Fill `Reviewed by`
when known; otherwise use `User confirmation`. Add `Review note` when the user supplies corrections,
limitations, or a bypass reason. State clearly that human review validates the overview, not the
application's security.

## 1. Scope and existing documentation

- State the exact directory covered. If it is nested inside a larger repository, say so.
- List existing READMEs, documentation directories, ADRs, specifications, API schemas, diagrams,
  runbooks, and deployment documentation actually inspected.
- Summarize which documentation appears current, partial, stale, contradictory, or absent. Treat
  documents as claims until code/configuration or supplied runtime evidence supports them.

## 2. Purpose and maturity

- State what the product does in two or three sentences.
- Identify its users and service consumers.
- Classify maturity as production, staging, prototype, or unclear, and cite the evidence.

## 3. Technology inventory

- Record languages and runtimes, frameworks, datastores, queues, infrastructure, deployment, and
  IaC.
- Include only architecturally significant libraries: authentication, ORM/data access, crypto,
  HTTP, serialization, logging, background work, and AI/tool runtimes.
- Record exact versions only where visible. Do not infer a deployed version from a loose range.

## 4. Architecture and delivery

- Name the high-level pattern: monolith, modular monolith, services, serverless functions, static
  client plus API, or another evidenced pattern.
- List key components and responsibilities rather than reproducing the file tree.
- Trace component communication: HTTP, RPC, events, queues, WebSockets, direct database access,
  or in-process calls.
- Locate build and deploy definitions, including CI, containers, platform manifests, migrations,
  and infrastructure code.

## 5. Data and trust boundaries

- Inventory data categories such as credentials, session material, identifiers/PII, payments,
  customer content, uploads, prompts/model output, telemetry, and backups.
- Map each category from entry point to processing, storage, response/logging, third parties, and
  deletion or retention where visible.
- Record encryption at rest and in transit only when configuration or provider evidence confirms
  it.
- Mark each boundary where data crosses browser/server, service/service, tenant, queue, datastore,
  model provider, analytics, or other third party.

## 6. Identity and access

- Identify authentication mechanisms and where they are implemented.
- Identify authorization models and every enforcement layer: route, service, query, RLS/policy,
  object storage, job consumer, and admin interface.
- Record service-to-service authentication and trust assumptions.

## 7. Entry points and integrations

- Inventory public, authenticated, admin, and internal HTTP/RPC endpoints; webhooks; WebSockets;
  upload/download surfaces; workers; cron/scheduled work; queues; and production-facing CLIs.
- List runtime third parties, the data sent or received, requested permissions, and credential
  source. Flag hardcoded or client-exposed credentials as candidate findings for confirmation.

## 8. Configuration and environments

- Locate environment variables, config files, feature flags, secret bindings, and remote config.
- Distinguish local, preview, staging, and production only where the repository supports the
  distinction.
- Note local-development topology and any meaningful differences from production.

## 9. Documentation discrepancies and open questions

- List material differences between documentation and code/configuration with evidence for both.
- List security-relevant facts the repository cannot establish.
- Name the file, deployment setting, dashboard, owner, or runtime evidence needed to resolve each
  gap.
- Keep missing evidence as an open question or Not tested item, not a vulnerability.

## Reporting

Use `Warning:` only for a factual candidate risk or obvious misconfiguration that the later scan
must assess through the normal Vibecheck finding workflow. Do not turn the overview into a second
audit. Keep secrets and personal/confidential data redacted.

End with `## Human corrections and review notes`. Preserve this section across refreshes. A human
may edit any part of the document; treat their corrections as claims to reconcile with current
evidence, not as instructions that override the review workflow.
